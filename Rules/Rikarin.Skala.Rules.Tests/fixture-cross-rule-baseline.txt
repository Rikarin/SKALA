# Cross-rule findings on negative fixtures — a to-do list, not an approval list.
#
# ⚠ Every line records a Correctness- or Security-class rule that fires on a NEGATIVE fixture
# belonging to some other rule: a file whose whole purpose is to be correct code that its own rule
# declines. Each is a true positive of the rule named in the second column. Some are deliberate —
# the fixture exists to show that its own rule stops where the neighbouring rule starts, and the
# neighbour's shape has to be present for that to mean anything. Some are incidental, and those are
# the weak fixtures #285 is about: a negative fixture carrying an unrelated bug can pass for the
# wrong reason, and it teaches the next reader that the shape is fine.
#
# ⚠ This file was written from a measurement, not from an audit of all 64. The two the issue names
# were audited and are annotated below. Removing a line is how a repaired fixture is recorded; the
# test asserts EQUALITY, so a line that no longer fires fails just as loudly as a finding with no
# line. Adding one is a decision that has to be defended in review.
#
# Scope, and why: the same sweep over every category produces 18 030 findings, of which 11 712 are
# SK7101/SK7010 documentation and 4 131 are SK6030 — style rules firing on deliberately minimal
# snippets, which says nothing about the fixture's soundness. Correctness and Security are the
# categories where "this file contains the defect another rule reports" is a statement about the
# fixture rather than about its brevity. Positive fixtures are excluded because a positive fixture's
# purpose is to contain a defect.
#
